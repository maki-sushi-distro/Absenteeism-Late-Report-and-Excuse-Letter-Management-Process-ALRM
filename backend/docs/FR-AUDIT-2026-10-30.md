# Backend review against the business requirements

Review date: 30 October 2026

Reference: BRD version 1.1.1, dated 28 October 2026, Functional Requirements FR-01 to FR-17.

## Scope and interpretation

This review compares the current backend with the requirements in the BRD. The backend is the part of the system that stores records, checks permissions, processes requests, and sends notifications.

The results below describe what the backend supports. Screen behavior for FR-01, FR-05, FR-09, FR-12, and FR-15 was confirmed by the project owner and was not independently checked in this review.

- **Implemented:** The main backend function is present.
- **Partly implemented:** The function is present, but part of the stated requirement still needs work.

| Requirement | Result | Explanation |
|---|---|---|
| FR-01 - Landing page | Implemented | The system provides a public introduction page, Google sign-in, and navigation to the correct dashboard. Screen behavior was confirmed by the project owner. |
| FR-02 - Google sign-in | Implemented | Students can create an account and sign in using their institutional Google account. |
| FR-03 - Automatic request routing | Implemented | Requests go to the instructor assigned to the student's selected class without manual forwarding. The student selects the class; the system does not choose a subject from the time of the absence. |
| FR-04 - Request and evidence submission | Implemented | Students can submit absence or late explanations and attach an optional PDF or image. |
| FR-05 - Evidence viewer | Implemented | Authorized Instructors and Program Heads can view attached evidence within their screens. Screen behavior was confirmed by the project owner. |
| FR-06 - Late-to-absence conversion | Implemented | Every three counted late marks add one absence hour. Currently, late marks are counted when the instructor marks the request Invalid. |
| FR-07 - Percentage and 20% maximum | Implemented | The system calculates the absence percentage as (absence hours divided by total subject hours) multiplied by 100. Total subject hours are the weekly class hours multiplied by 16 weeks. Every three counted late marks add one absence hour. The maximum absence allowance is 20% of total subject hours, rounded up to a whole hour for every subject: 7 hours for a subject meeting 2 hours per week, 10 for 3 hours per week, and 16 for 5 hours per week. |
| FR-08 - Attendance warnings | Partly implemented | Preventive, Critical, and Drop Limit warnings are present. However, a Critical warning can be cleared without a recorded consultation. Notices show hours used, the limit, and the remaining percentage, but do not directly state how many absence hours remain. Automatic background checking also needs to be set up. |
| FR-09 - Dashboards for each role | Implemented | Each role has a dashboard with access to relevant records. Screen behavior was confirmed by the project owner. |
| FR-10 - Links in request notifications | Implemented | Instructors receive automated email and in-app notifications with links to review requests and approve or invalidate them. The request-opening behavior was confirmed by the project owner. |
| FR-11 - Decisions and student notifications | Implemented | The instructor's decision is saved, recorded in the activity log, and sent to the student through email and in-app notifications. Automatic screen updates still need to be checked. Allowing one missed assessment remains the instructor's responsibility. |
| FR-12 - My Records | Implemented | Students can view their own request history and details, grouped by month, with All, Late, and Absent tabs and a subject filter. Screen behavior was confirmed by the project owner. |
| FR-13 - Student follow-up | Implemented | Students can follow up only on their own Pending requests. The instructor is notified, and the follow-up is recorded in the activity log. |
| FR-14 - Notification center | Partly implemented | Users can retrieve notifications, check unread counts, and mark notifications as read. A student does not receive a separate confirmation notification after sending a follow-up. A separate notification for being marked Late or Absent was not found. |
| FR-15 - Instructor assignment | Implemented | Administrators can assign, edit, and remove instructor assignments and filter the assignment list by program. Screen behavior was confirmed by the project owner. |
| FR-16 - Activity log | Implemented | The main read-only log records Submitted, Followed up, Approved, and Invalid actions with related request information. The screen supplied by the project owner shows Action, Subject, and Date filters. Administrators can access college-wide entries, while primary Program Head accounts access entries within their program. Access for an instructor who also serves as Program Head remains a separate issue with that additional account arrangement. |
| FR-17 - Instructor class requests | Partly implemented | Instructors can retrieve requests assigned to them. The supplied screen shows a class list, a subject filter, and a View button. The student records shown after selecting View have not been checked, so Late and Absent tabs with counts, date filtering, monthly grouping, Minutes Late, absence percentage, and warning highlights remain unverified. The backend request list does not itself include absence percentages; the record screen may obtain them separately. |

## Additional features included in this review

The following features are implemented but are not all described separately in FR-01 to FR-17. Some expand an existing requirement. Reports are already included in the BRD's project scope, even though they do not have a separate numbered FR.

| No. | Feature | Plain-language description |
|---|---|---|
| 1 | Email verification codes and trusted devices | Users may need to enter a code sent to their email when signing in. They can request another code. A recognized device can skip this extra step. |
| 2 | Administrator account management | Administrators can create accounts, change a user's role, approve or deactivate accounts, and remove eligible accounts. Accounts with teaching or enrollment history are protected from removal. |
| 3 | Profile completion and information checks | The system collects and checks details such as school ID, program, year level, guardian name, and contact number. Some details are required before a student can complete a request. |
| 4 | Email notification preference | Users can choose whether to receive optional system notification emails. Sign-in verification codes are handled separately. |
| 5 | Editing and cancelling Pending requests, and the Noted status | Students can edit or cancel requests that have not been reviewed. Instructors can also mark a request Noted, in addition to Approved or Invalid. |
| 6 | Instructor assignment history and change safeguards | The system keeps a history of instructor assignments and allows assignments to be exchanged. Old requests keep the class and instructor details recorded when they were submitted. The system checks whether an assignment has changed since it was opened and prevents assignment changes while requests are still Pending. |
| 7 | Curriculum and program subject lists | The system stores curriculum and masterlist information, including the subjects offered by each program. It can keep different curriculum versions so changes do not replace the earlier curriculum records. |
| 8 | Class and meeting details | Administrators can create classes and maintain meeting days, times, rooms, hours, semesters, and school years. This needs to be reconciled with the BRD because its scope excludes creating or managing class schedules. |
| 9 | Closing follow-ups | Instructors and Program Heads can mark follow-ups assigned to them as resolved. This records that the follow-up has been addressed. |
| 10 | Report preview and downloads by role | Administrators can preview and download reports. Instructors and Program Heads have report downloads limited to the records they are allowed to see. Administrator and Instructor downloads use Excel files; Program Head downloads use CSV files that can be opened in Excel. PDF downloads were not found. |
